Redundancy And Complexity Audit

The strongest finding is that Flaming Horse has several overlapping owners for the same responsibilities. The project is deterministic in intent, but the current implementation spends compute and code on repeated validation, repeated state repair, repeated voice-cache preparation, and repeated repair entry points.

Status: analysis artifact Updated: 2026-05-19 Scope: no runtime changes

Headline Shape

Largest gravity well

scripts/build_video.sh is still the largest runtime surface and owns orchestration, validation, repair, render, QC, state mutation, diagnostics, and notification.

Extraction underway

The live path now has a dedicated scene validator, but several validation, state, cache, and render checks still need ownership cleanup.

Best next test seam

Extract one deterministic scene-validator interface before larger refactors. That gives a small executable target without changing phase behavior.

Specific Redundancy Findings

Priority Redundant Or Complex Construct Live Surfaces Why It Hurts Smallest Safe Bite
P1 Scene validation has multiple owners. harness_responses/parser.py, scripts/scene_validator.py, scripts/build_video.sh validation functions, scripts/validate_scene_timing_budget.py, scene_qc, final render guards. The same bad scene pattern can be accepted, rejected, repaired, or logged differently depending on the phase. This makes refactors hard and wastes dry-run/render work. Create scripts/scene_validator.py with named gates and JSON output. First port only existing checks; do not add new rules in the extraction patch.
P1 State transition ownership is split between deterministic state code and direct shell-embedded Python mutations. scripts/update_project_state.py, apply_state_phase, normalize_state_json, many inline json.load/json.dump snippets in build_video.sh. project_state.json is supposed to be script-owned, but many local snippets mutate phase, errors, flags, history, and scene metadata directly. That blurs the single source of truth. Add one update_project_state.py --mode record-error or equivalent narrow operation, then replace one repeated inline error mutation cluster.
P1 Phase success is allowed even when deterministic state application is ignored. apply_state_phase "plan" || true, apply_state_phase "review" || true, apply_state_phase "narration" || true, apply_state_phase "build_scenes" || true, main loop post-phase apply_state_phase "$current_phase" || true. A phase handler can report success while state fails to advance. The main loop then applies transition again and normalizes again, hiding the first failure site. Add a no-progress sentinel around one phase first, probably plan, and require one of: phase/index advanced, human review set, or nonzero return.
P2 Repair entry points are scattered. build_scenes gate repair, scene_qc runtime repair, final_render syntax repair, final_render ShowCreation repair, render-failure repair, and removed legacy self-heal surfaces. Repair remains available in too many contexts with different reasons, counters, and diagnostics. That makes it hard to measure whether first-pass generation is improving. Introduce one invoke_scene_repair_for_gate(scene, gate, reason) wrapper and route all live repair calls through it. Keep behavior identical.
P2 Voice cache preparation is repeated in several phases. create_video.sh calls prepare_voice_service.py; precache_voiceovers phase calls precache_voiceovers_qwen.py; runtime validation calls ensure_qwen_cache_index; final_render calls handle_precache_voiceovers when cache is missing. Voice setup is expensive and has old Qwen naming despite backend-neutral MLX/Qwen behavior. Rechecking is fine; regenerating or branching in multiple places is not. Define one ensure_voice_cache(project_dir, mode) command with check-only and build modes. Replace only ensure_qwen_cache_index first.
P2 Scene metadata inference is duplicated. scripts/resolve_scene_metadata.py, infer_scene_class_name, get_current_scene_id, get_scene_narration_key, final-render metadata repair. Scene id, file, class name, and narration key can be inferred differently in different code paths. This threatens deterministic behavior when generated state is partial. Create one Python resolver that returns {scene_id,file,class_name,narration_key} for an index. Use it in build_scenes first.
P2 Artifact recovery from logs competes with parser-owned artifact writing. handle_plan recovers plan.json from build.log; handle_narration recovers narration_script.py from build.log; harness_responses/parser.py already owns artifact promotion. Log scraping is brittle and keeps legacy behavior alive after the Grok CLI staged-JSON contract. It adds many lines for a path that should be impossible if harness output is mandatory. Document current recovery as legacy containment, add a test that harness failure returns nonzero when artifact is not written, then remove one recovery block.
P2 Interpreter ownership is still inconsistent outside the core build runner. Entrypoint and project-creation helpers now share PYTHON_BIN; remaining interpreter drift should be checked in any new helper scripts. The entrypoint can validate one interpreter and run helper code under another. That hurts reproducibility and makes local Mac setup bugs harder to classify. In create_video.sh, use PYTHON_BIN for path resolution, voice prep, and build-arg parsing. Keep this as a one-file patch.
P3 Stale docs and dead patch files describe non-live paths. docs/validation/VALIDATION.md, CURRENT_STATE.md, parts of TECH_SPEC.md, historical harness/ docs. Agents and humans can follow a non-live path and make fixes against old surfaces. This creates wasted review rounds. Keep active docs pointed at live runtime surfaces and keep historical docs clearly labeled.
P3 Final render owns too much post-build logic. handle_final_render clears state errors, ensures voice cache, repairs metadata, extracts scene lines, validates/render-verifies each scene, handles transient retries, repairs render failures, writes scene verification, advances phase. Final render is doing orchestration, validation, recovery, render execution, and state persistence. It is hard to test without a full video render. Extract verify_scene_video and update_state_rendered into small scripts first. Those can be tested with fake mp4 metadata fixtures.

Refactor Safety Strategy

  1. Extract before changing behavior. Move one responsibility into a testable module while preserving exact output and exit behavior.
  2. Choose one owner per responsibility. After extraction, the shell runner should call the owner rather than duplicate the rule.
  3. Add characterization tests first. Use small fixtures for state JSON, scene files, and fake cache indexes.
  4. Retire dead surfaces immediately after replacement. Keeping old helper scripts around as documentation invites drift.
  5. Measure compute reduction. Track dry-runs, repair calls, precache invocations, and render attempts per run.
Best first bite: extract scene validation into one Python command that can run against a fixture project and return stable JSON. This removes the most dangerous overlap without changing the user entrypoint or the phase sequence.

Suggested Test Seams

Test Seam Fixture Needed What It Proves
scene_validator.py --project-dir fixture --scene scene_01.py --json One scaffolded scene, one invalid API scene, one timing-missing scene. Scene gates classify failures without invoking the full pipeline.
update_project_state.py --mode apply --phase ... Minimal state plus phase artifact files. Each phase advances or fails deterministically.
resolve_scene_metadata.py State files with complete, partial, and malformed scene entries. Scene id/file/class/narration resolution is identical across phases.
ensure_voice_cache.py --check Voice config, narration script, empty cache, partial cache, complete cache. Voice-cache readiness is checkable without rendering or generating audio.
verify_scene_video.py Small mp4 with audio, mp4 without audio, missing output. Render verification can be tested apart from Manim scene generation.

Non-Goals For This Cleanup Track

  • Do not add new rendering modes.
  • Do not weaken repair behavior while extracting validation.
  • Do not hand-patch generated projects.
  • Do not change the canonical user entrypoint.
  • Do not combine visual-quality improvements with ownership extraction in the same patch.
